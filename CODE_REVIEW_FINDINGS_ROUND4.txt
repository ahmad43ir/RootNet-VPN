 🟠 HIGH

🟠 Pipeline: every scraped config was invisible to the app — `premium_only=true`
   hardcoded for ALL scraped links (v1 leftover) — FIXED
   Issue:
     vless-scraper/main.py (persistent `_handle_message` + run-once `scrape_once`)
     set premium_only=True on every scraped link; the worker honored it; the
     import RPC copied it into `servers`. But the v2 app reads `servers` as anon,
     and RLS (20260721000001) only exposes `is_active=true AND premium_only=false`.
     With no accounts/JWT in v2, NO user could ever see a scraped config — only
     manual bot uploads fed the app. Directly contradicted the bot copy ("configs
     … flow straight into the app").
   Fix: Removed the premium concept END-TO-END (scraper + worker + bot + app +
     DB + rootnet-api + docs) — see the FIXED section. All servers are now public.
   References: main.py:607/899 (old); RLS 20260721000001; migration
     20260815000001_remove_premium_only.sql (new).

🟠 Scraper: cursor + limit silently skipped messages forever on busy channels — FIXED
   Issue:
     scrape_once fetched min_id=cursor, limit=3 and advanced the cursor to
     messages[0].id (the NEWEST). If a channel posted >3 messages between runs,
     the older ones were never read and the cursor jumped past them — permanent
     data loss on firehose channels.
   Fix: New `_fetch_new_messages()` — top batch, then walk BACKWARD (Telethon
     reverse=True, ascending) through the gap until a short/empty batch proves
     the channel is caught up; cursor advances to the newest id only then, else
     to the top of the drained chunk (next run resumes there). New
     RUN_ONCE_MAX_MESSAGES_TOTAL (default 30) caps total reads per channel per
     run — matching AGENTS.md's ≤30 msgs/channel. Verified with a mocked-Telethon
     simulation: 10-run firehose (reads never exceed 30/run, cursor monotonic,
     no skips), full-drain reaches the top (508/508), 6 edge cases pass; the
     sim caught a real off-by-one (Telethon max_id is EXCLUSIVE — the initial
     bound skipped the message right below the top batch; fixed).
   References: main.py `_fetch_new_messages`; scrape.yml RUN_ONCE_MAX_MESSAGES_TOTAL.

🟠 Scraper: FloodWait was capped at 300s and then continued — FIXED
   Issue:
     Both FloodWaitError handlers slept min(e.seconds, 300) then `continue`.
     AGENTS.md says honor FloodWait (sleep_for(seconds)), never catch-and-continue:
     continuing after a truncated sleep just re-triggers the wait, and a full
     long sleep blows the 10-min Actions timeout.
   Fix: New FLOOD_WAIT_ABORT_SECONDS (default 120, env-tunable) + async
     `_handle_flood_wait()`: waits below the threshold are slept in FULL; waits
     ≥ threshold raise FloodWaitAbort → scrape_once breaks out of the remaining
     channels and run_once_mode logs a clear message + exits code 2 (visible
     failure in Actions, no wasted minutes). Persistent mode untouched (no job
     timeout budget there). refresh_pool handles FloodWait internally — verified
     the outer handler only needs FloodWaitAbort.
   References: main.py FloodWaitAbort / _handle_flood_wait; run_once_mode.

🟠 Workflow: bot-managed channels could never run without the CHANNELS secret — FIXED
   Issue:
     _validate_config() hard-failed on empty CHANNELS, and scrape.yml skipped the
     run entirely when CHANNELS was unset (TG_READY gate). But at runtime
     get_vless_channels() prefers scraper_config.vless_channels (bot /addchannel).
     An admin who only used /addchannel got ZERO runs.
   Fix: _validate_config() now only requires CHANNELS when the storage backend
     can't supply a list (create_storage().supports_config() — true for Supabase,
     false for local JsonStorage); scrape.yml TG_READY no longer requires
     CHANNELS != ''; header comment + "No Telegram credentials yet" message
     updated. Also added `set -o pipefail` to the run step so a scraper error
     marks the job failed instead of being masked by `tee`.
   References: main.py _validate_config; scrape.yml TG_READY / run step.

 🟡 MEDIUM

🟡 Pipeline: REST budget creep from per-message vpn_files calls — FIXED
   Issue:
     Every document message triggered 2 REST calls (vpn_files GET check + POST
     insert) in `_upload_attachment_file`, EVEN when the document yielded no
     config links. On document-heavy runs that's 30+ REST calls on top of the
     normal budget — AGENTS.md targets ≤ ~20 per run.
   Fix: `_upload_attachment_file` now runs only when the attachment actually
     yielded config links — both call sites guard on `file_links` (after the
     merged-links early return). Files with no extractable configs are never
     downloaded for upload nor GET/POST'd. Also added `.npvt` to
     CONFIG_EXTENSIONS so parse coverage matches the upload list (was: uploaded
     but never scanned). py_compile OK.
   References: main.py `_upload_attachment_file` + both call sites; AGENTS.md
     Supabase budget.
